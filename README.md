# Secure Subscription Collector

Автоматический сборщик и валидатор подписок для Android-клиентов, совместимых с URI-форматами **VLESS**, **Trojan**, **Hysteria2** и **TUIC v5**. Проект получает подписки из `input.txt`, отбрасывает неполные и небезопасные профили, проверяет оставшиеся профили через несколько URL и публикует один очищенный `output.txt`.

> Проверка выполняется через сам профиль: для каждой конфигурации запускается временный изолированный маршрут, а запросы направляются через него. Это не является гарантией постоянной работоспособности узла, но отсекает профили, не прошедшие заданный URL-кворум во время запуска.

## Поддерживаемые протоколы

| Протокол | Требования статического фильтра |
|---|---|
| VLESS | UUID; TLS с SNI и fingerprint либо Reality с `encryption=none`, SNI, fingerprint и `pbk` |
| Trojan | Пароль, TLS, SNI и fingerprint |
| Hysteria2 / `hy2` | Пароль, TLS и SNI |
| TUIC v5 | UUID, пароль, TLS, SNI и версия `5` |

Все остальные схемы исключаются. Профили с `allowInsecure=1` или `insecure=1` не публикуются.

## Единый выходной файл

`output.txt` полностью перезаписывается при каждом успешном обновлении. Профиль сохраняется в исходном совместимом URI-формате, а его имя после `#` получает короткий ASCII-фрагмент:

```text
TYPE-SECURITY-TRANSPORT-CODE
```

Примеры:

```text
VL-REALITY-GRPC-3ScvEG
TR-TLS-TCP-3ScvEG
HY2-TLS-UDP-3ScvEG
TUIC-TLS-UDP-3ScvEG
```

`CODE` — стабильный шестизначный буквенно-цифровой идентификатор. В имени нет IP/домена, SNI, UUID, пароля, ключа или исходного названия из сторонней подписки. Используются только буквы, цифры и дефисы, поэтому Android-клиенты отображают имя без URL-кодирования `%20` и специальных символов.

## Дедупликация

Дубликаты с одинаковыми параметрами подключения удаляются независимо от порядка query-параметров или исходного имени. При этом профили с одинаковыми сервером и портом, но разными SNI, Reality-ключами, TLS-параметрами, транспортом или другими соединительно значимыми полями сохраняются как отдельные конфигурации.

## URL-проверка

Каждый статически допущенный профиль проверяется через временный sing-box outbound. Для одного профиля одновременно запускаются четыре HTTP(S)-запроса:

| URL | Ожидаемый код |
|---|---:|
| `https://www.gstatic.com/generate_204` | 204 |
| `https://www.google.com/generate_204` | 204 |
| `https://cp.cloudflare.com/generate_204` | 204 |
| `https://www.apple.com/library/test/success.html` | 200 |

Профиль попадает в `output.txt`, если успешно отвечает минимум на **2 из 4** запросов. Для каждого контрольного HTTP(S)-ответа через профиль действует предел **300 мс**; запуск временного локального маршрута ограничен отдельным тайм-аутом в 3 секунды. Для успешных запросов рассчитывается медианная задержка; в отчёт попадают только агрегированные счётчики без URI, адресов, SNI, учётных данных и содержимого ответов. Профили обрабатываются асинхронными батчами по 32 с одновременной проверкой не более восьми профилей: это ограничивает пиковое потребление ресурсов и сохраняет правила кворума.

## Журнал выполнения

Команда `python -m subscription_collector` выводит русскоязычный журнал в стандартный вывод GitHub Actions. Для каждого этапа — подготовка, загрузка источников, статическая фильтрация, удаление повторов, URL-проверка и публикация — журнал показывает начало, завершение, длительность и агрегированные счётчики. Информационные сообщения сетевого транспорта `httpx` и `httpcore` с отдельными HTTP-запросами подавляются. Во время URL-проверки выводится безопасный количественный прогресс, а для отклонений указывается номер профиля в текущем запуске и понятная причина, например тайм-аут, ошибка HTTP или ненабранный кворум.

В журнал не попадают URI, домены, IP-адреса, SNI, ключи и учётные данные. В `report.json` также сохраняется объект `timing_ms` с агрегированными длительностями этапов.

## Файлы проекта

| Файл | Назначение |
|---|---|
| `input.txt` | Публичные HTTPS URL подписок: один адрес на строку |
| `output.txt` | Единый очищенный список прошедших проверку профилей |
| `report.json` | Агрегированные причины исключения, свежесть источников и итоги проверок |
| `.collector/state.json` | Хеши профилей и даты первого/последнего наблюдения без секретов |

## Автоматическое обновление

Обновление подписок запускается **только вручную** или по расписанию — каждые четыре часа. При обновлении workflow загружает фиксированный релиз sing-box для Linux, проверяет SHA-256 архива, выполняет статическую фильтрацию и URL-проверки, а затем коммитит только изменившиеся `output.txt`, `report.json` и `.collector/state.json`.

Изменение кода не запускает сбор или URL-проверки. В расписании профили обрабатываются батчами по 32, внутри каждого батча одновременно проверяется до восьми профилей; это безопасный компромисс между скоростью и потреблением ресурсов, поскольку каждая проверка запускает отдельный процесс `sing-box`.

## Ограничения

Возраст отдельного URI невозможно достоверно установить, если источник не передаёт дату публикации; при наличии HTTP `Last-Modified` применяется окно свежести 72 часа. Результат URL-проверки зависит от сети запуска и доступности контрольных URL в момент выполнения. Импорт и использование опубликованных профилей остаются под контролем пользователя.
